# korbat account lifecycle (1b) — execution prompts

One file per task. Each file is a complete, self-contained prompt: paste the whole file into a fresh Claude Code session opened at `C:\Users\Lenovo\Desktop\cool\korbat` and let it run. Do them in order. Every prompt checks that the previous task's commit is the latest one before it starts.

## How these prompts were made reliable

Every task was dry-run end to end on 2026-09-24 in a scratch clone of this repository, one commit per task. For each task a runner wrote the tests, ran them and required the expected failure, and wrote the implementation. It then ran every verification command and required each expected line, refused any changed file outside the task's list, and only then committed. These prompts are generated from those commits and the recorded outputs. Every file block is the committed file, and every "Observed on the dry run" block is real output. The scratch clone used shifted ports and its own compose project; the prompts use this repository's real ports and commands.

The dry run found and settled these points before the prompts were written:

- **A bio is one line.** `Bio` refuses every control character, tab and line feed included; a post body allows tab and line feed. The profile screen shows the bio as one line of plain text.
- **`MeProfile` extends `Profile`.** `/api/me` needed the two new profile facts (`handleChangedAt`, `verified`), so the contracts add `MeProfile = Profile.extend(...)` for `MeResponse.profile` and leave `OnboardingHandleResponse` on the three-field `Profile`; the profile store's `find` reads the two columns.
- **Blank Vonage credentials count as absent.** Compose passes an empty `infra/.env` line as an empty string, so `VONAGE_API_KEY` and `VONAGE_API_SECRET` treat an empty string as unset; the production guard for `vonage` then fires as intended.
- **`PhoneCode`** (six digits) names the badge code instead of reusing `EmailCode`, so the two flows can diverge later.
- **The handle change locks the row.** `changeHandle` in the social repository takes the profile row `for update`, checks `profiles` and `handle_history` in one snapshot and inserts the old handle with `on conflict do nothing`; the unique index makes the loser of a race `handle_taken`. Its limit key is `social:profile-edit:<user>`, with the module prefix every social bucket has.
- **`AuthErrorKind`.** `AuthError` was typed to the contracts' `AuthErrorCode`, which has no `invalid_request`; the same-address refusal needs it, so `context.ts` widens the error's code to `AuthErrorKind = AuthErrorCode | "invalid_request"` as the social and media modules do. No consumer narrows on the old type.
- **Order of checks in the email change.** The same-address check runs before any limit, so a slip never puts the account's own address on the sign-in cooldown; at verification the code row's owner and purpose are checked before `checkEmailCode`, so another account's flow id costs the owner no attempt, an unknown flow id is `invalid_code` and an expired code is `code_expired`. The cooldown refusal carries `Retry-After: 60` (the sign-in start's refusal does not, a 1a leftover left alone) and the `email_changed` event carries the device id next to the two address hashes.
- **A memory auth harness.** `apps/api/test/auth/flow-harness.ts` is new: a fake `AuthRepo` with only the methods the flows call (`satisfies Pick<AuthRepo, ...>`), memory key-value store and mailer, a fixed clock and recorded events; the badge and deletion tests reuse it.
- **The Mailpit test proves the move with password sign-in.** The change start puts the new address on the 60-second per-address cooldown (a real Redis TTL in that suite), so a code sign-in right after the change is `rate_limited` by design; the test signs in with the password at the new address and is refused at the old one.
- **`AuthErrorStatus` gains 404** for `badge_unavailable`; the union was `400 | 401 | 403 | 409 | 429 | 503`.
- **The pending badge state carries its expiry.** `KeyValueStore.set` cannot keep a key's TTL, so counting an attempt writes the state back with what is left of the original ten minutes (`expiresAt` in the state) instead of a fresh ten minutes; once they pass the store has dropped the state and the answer is `invalid_code`. On a right code the state is deleted before the phone hash is written, so a `phone_in_use` conflict ends the flow (Vonage has spent the request) instead of leaving a replayable state; `code_expired` from the provider deletes it too.
- **`verifyBadge` answers `badge_unavailable` too** when the provider is off, and `removeBadge` works with the provider off: it clears both columns even without a badge (silently, no mail or event), which also finishes a removal that stopped between its two writes. Badge events carry no metadata, not even the hash.
- **`verificationProviderFrom(config)`** (exported by `auth/index.ts`) throws at start-up when `vonage` lacks credentials, in development as well as production; `vonageProvider` takes a `timeoutMs` (default 10 000) so the timeout test does not wait ten seconds.
- **The badge code's messages.** The reused `invalid_code` and `code_expired` messages say "check the latest email"; the web app's badge section shows its own wording for those two codes.
- **`export.json` is written last.** The images are streamed first, so `missingMedia` can name every image whose file was gone when its turn came, without holding file descriptors or racing a stat against an open; entry order is irrelevant to readers, and the unit test pins it.
- **The ZIP writer treats the store as untrusted.** `addFile` opens with `O_RDONLY | O_NOFOLLOW | O_NONBLOCK` and checks `isFile()` before adding the entry, as `media/files.ts` does: a symlink, FIFO or directory planted in the store counts as a file that cannot be opened (it lands in `missingMedia`), not as a leak. Images are stored, `export.json` deflated; sizes and checksums travel in data descriptors so the archive streams without knowing any size up front.
- **Export facts settled here.** `account.verified` comes from the auth row's phone hash; `devices` excludes revoked ones; `handleHistory` appends the current handle when it is not yet in `handle_history` (it is only there after a return to an old handle); `exportImages` includes ready images not on a post; events are bounded to the 90-day retention even though the janitor purges them. The daily limit is taken before anything is built (`Retry-After` on refusal, 503 when the limit store is down), the JSON is built before the first byte, and the `export_created` event is appended after the last chunk; a stream that fails after the 200 can only be logged (a truncated archive) and still counts as the day's export.
- **Architecture rule.** The account module imports no table or enum of either schema (`Db`/`DbTx` types allowed); `MODULES` in the architecture test gains `account`.
- **The bundle's require shim is aliased (Task 5).** esbuild prepends the banner verbatim and cannot rename its names; fflate's ES module imports `createRequire` from `module` at top level, so with the plain name the bundle declared it twice and Node refused to load it (`SyntaxError: Identifier 'createRequire' has already been declared`), which only the container start showed: the unit and integration tests never load the bundle and esbuild does not check the banner. `build.mjs` now imports it as `createRequireForBundle`, and Task 5 gains a `node --check apps/api/dist/index.js` step after the build. Task 7's stack rebuild found it.
- **The purge locks the profile row.** `purgeProfile` takes the profile `for update` first, so the request's purge and the job's cannot interleave; the parents' reply counters and the quoted posts' quote counters are adjusted in one statement each before the tombstoning (a self-reply's parent is written once per statement); the current handle is inserted into `handle_history` (on conflict do nothing) so the reservation no longer depends on the anonymised profile row; the profile is anonymised only while `deleted_at` is null. A second run changes nothing, proven on Postgres.
- **`finishPurge` writes only a deleted, not-yet-purged row**, so it is a no-op when already purged and never touches a live account; `pendingPurges` is oldest first, at most 100.
- **The sign-in flows needed no change:** `findUserByEmail`, `findUserById` and `findActiveSession` already exclude rows with `deleted_at`; the tests prove a deleted address answers as an unknown one (same shape, padded time) and password sign-in is `invalid_credentials` with no failure recorded.
- **The smoke test uses a second throwaway account** for the lifecycle: the grant-role check at the end revokes every session of the first account, and a deleted account cannot be granted a role. The second account posts once and the script checks the post has left the Latest timeline after deletion. The image files' removal is asserted through a deletion request in `uploads/deletions` for every image id of the owner, the media tests' convention; the worker deletes the files.
- **Purge failures.** When the purge throws after the auth confirmation, the route logs it and still answers 204: the account is gone whatever happens next, and the job finishes it. A round of the job logs `{ purged, failed }` only when it did something, as the janitor does.
- **`SettingsNav` takes `current` as a prop** instead of reading `usePathname()`: expo-router cannot be imported under vitest (it fails to parse in the Node environment), so the test mocks `expo-router` with a `Link` that hands its child the `href`, and react-native-web renders the real anchors with `aria-current`. Every screen passes its own name; a source scan checks that each settings screen renders the row.
- **Screen details settled here.** The Delete button stays disabled until the typed handle matches case-insensitively (the API's `handle_mismatch` would otherwise surface as the generic `invalid_request` text); on `badge_unavailable` the section shows the API's message and only `EXPO_PUBLIC_BADGE=off` hides it; the export button is web-only (`Platform.OS === "web"`, native shows a note) and `lib/download.ts` accepts only a filename of the API's own shape from `Content-Disposition`, falling back to `korbat-export.zip`; the cooldown date shows from `handleChangedAt + 30 days` and is replaced by the `Retry-After` date after a `handle_cooldown` answer; the profile screen loads the bio from `GET /api/profiles/:handle`, which `/api/me` lacks.
- **The terms text changed without a version bump.** `TERMS_VERSION` stays `draft-2026-09`, as the audit's terms change did; the terms text lives in `apps/app/src/lib/terms.ts` and `terms.tsx` only renders it. `Section` moved from the security screen into `components/ui.tsx` next to the new `VerifiedChip`, and `lib/api.ts` gained `PATCH`, `ApiError.retryAfter` (parsed from `Retry-After`) and `apiResponse()`, which returns the raw `Response` for the ZIP.
- **One undo link per account per 24 hours (Task 8).** Minting a link for every change can be beaten: an attacker moves the account A to B, then B to C, and receives the link that is sent to B. Once the owner has used the link sent to A, the attacker's link moves the account back to B for good. So only the first change in a 24-hour window mints a link, and later changes send a notice without one. What was set after the change is judged from `users.password_changed_at` and `totp_enabled_at` against the change time, which also catches a changed password. TOTP is cleared with the existing `disableTotp`. A link for an account deleted since is refused like a used one. A revert that fails with `email_in_use` still spends the link.
- **Badge start buckets in order (Task 8):** account, IP (10 an hour), number, then the instance-wide ceiling (200 a day) last. A start refused by a narrower bucket therefore spends nothing of the wider ones. Attempts are counted with `kv.incr` on their own key after the ownership and expiry checks.
- **`for key share`, not `for share` (Task 8).** With `for share` on the followee's row, ten concurrent follows of one account deadlocked (40P01): each follow's counter update conflicts with the other follows' share locks. `for key share` still conflicts with the purge's `for update`. Both accounts' rows are locked, so a write by the account being deleted is refused too, and `bookmark` now runs in a transaction.
- **Deletion step 1 is `takeDown` (Task 8).** It is one transaction: mark deleted, revoke the session rows, delete devices and codes, append the event. It returns the revoked session ids, which are tombstoned afterwards, best effort. The `account_deleted` mail goes after the commit. `finishPurge` first runs `finishTakeDown`, the same row steps again and idempotent, so the job finishes a step 1 that failed after the mark. The now-unused `deleteDevices` and `deleteEmailCodes` are removed.
- **Lock tests are bounded (Task 8).** Their pool sets `lock_timeout` 5 s, `statement_timeout` 15 s and `idle_in_transaction_session_timeout` 30 s as URL parameters. Every lock holder is released in a `finally`, each test has a 30-second limit, and waits are detected through this database's `pg_stat_activity`. An earlier full run sat for 14 hours after the machine suspended.
- **The ZIP container is korbat's own (Task 8).** fflate 0.8.3 has no ZIP64 and does not export `crc32`, so `zip.ts` writes the headers, data descriptors, central directory and ZIP64 records itself. It keeps fflate's `Deflate` for `export.json` and takes the CRC from Node 24's `node:zlib` `crc32`. ZIP64 turns on at 0xFFFFFFFF and at 65,535 entries or more, because those values are themselves the "see ZIP64" markers. The test-only options `{ zip64: "always" }` and `startOffset`, plus a fake 4 GiB + 1 file of zeros, prove the switch. Python's `zipfile.testzip()` and `unzip -t` both accept the forced-ZIP64 archive.
- **export.json streamed (Task 8).** An async generator writes the document member by member. It reads the social lists in keyset pages of 1,000 on `(created_at, id)`, with page keys that keep microseconds: keys cut to the millisecond looped forever. `addJsonPieces` feeds the deflate at most 64 KiB at a time and yields to the event loop between feeds. The output is byte-identical to `JSON.stringify(document, null, 2)`, proven on fakes and on Postgres with a page size of 2.
- **The export stream (Task 8).** The route builds its body from a `TransformStream` and aborts it on failure, so the download fails visibly. `export_created` is recorded just before the body closes. A failure before the first byte gives the day back through the new `RateLimitStore.release` (a Lua script on Redis). Image files go through `openImage`, which checks for a regular file on the same device of at most 32 MiB, and are read only to the checked size.
- **Lock coverage completed (Task 8).** `block`, `mute` and `createPost` take the same `for key share` lock as the other writes. A post by an account being purged is `not_found`; a reply to or quote of a post whose author is being purged is `post_unavailable`. Twelve concurrent blocks, mutes and replies aimed at one account did not deadlock. The email revert also revokes every device of the account, through the new `revokeDevices` repository method.
- **Web details (Task 8).** Each action begins with its button's condition, so Enter cannot bypass a disabled button. The account's own address is refused before the API is called. Code fields take `autoFocus`, and `useFocusOnReturn` puts the focus back after Start over, Cancel, Change, Verify and Remove badge; `Field` and `Button` forward their refs. The export's limit message names the hours. The Verified chip is `role="img"` with its label. The badge section needs `EXPO_PUBLIC_BADGE=on`, which `apps/app/.env.example` sets for development and `WEB_BADGE` sets for the Docker build (the default is off).

Each prompt replaces judgment with rules. Files are complete and copied byte for byte, commands run verbatim, and every expected line must appear. Any mismatch is a **STOP condition** that ends the session with a report instead of an improvised fix. The single permitted self-recovery is a clean `node_modules` reinstall after a `Cannot find module` error in a verification step.

## What can differ between runs

- **Run noise.** Timings and commit hashes differ on every run; every install prints `Packages: -N`, the optional packages pnpm skips on Windows.
- **Durations.** The integration suite runs its files one at a time since `67b7171` and takes a few minutes; the web export runs a full Metro bundle and can take a few minutes.
- **The sign-in timing check** (`auth-flows-mfa.test.ts`, integration) needs a quiet machine; if it fails once with a difference just over 50 ms, run the integration step again, and treat two failures in a row as a defect.
- **Task 5's install prints `Packages: +5 -163` (or similar).** The hoisted linker re-lays out `node_modules`; the lockfile diff is only the three fflate lines.
- **`social-repo.test.ts` "threads" once timed out at 5 s** after `createPost` gained its lock statements; it takes 1.1 to 1.3 s on every other run. Rerun the integration step once before treating it as a defect.

## Before you start

- **Files are written by a script, never typed.** A file block can contain backslash escape sequences, and a writing tool can decode those into the characters they stand for; the 2b dry run's own tooling did exactly that once. These prompts were replayed into the repository by `replay.py` in the scratch tooling, which runs exactly these steps without a model session; a fresh session following them by hand must reach the same commits. Every writing step therefore runs `write_blocks.py`, which copies the step's blocks from the committed prompt file byte for byte, and `verify_prompts.py` checks the result after the last task.
- Every gate in the dry run ran with its standard input closed and a time limit. If a step sits without output for much longer than its allowed difference says, it is stuck, not slow: stop it and report.

## Reading a report

Every session ends with a `TASK N REPORT` block. Check three lines before starting the next prompt:

1. `STOP condition hit: none`. If not, the session stopped on purpose. Read the pasted output, fix the environment (Docker not running, a port in use, data services down), and re-run the same prompt from a clean `git status`.
2. Every `Verify` line shows the expected text from the prompt.
3. The `Commit` line ends with the commit subject printed in the prompt.

If a report shows a STOP that is not an environment problem, paste the report back to the planning session. Do not let the executing session improvise.

The design is `docs/superpowers/specs/2026-09-24-account-lifecycle-1b-design.md`, including its amendments from the dry run. The task map is `docs/superpowers/plans/2026-09-24-account-lifecycle-1b.md`. Where the plan and a prompt differ, the prompt is the verified version.
