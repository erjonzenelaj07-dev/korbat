# korbat sub-project 3a: the staff console foundation

Date: 2026-09-28. Status: written without the user under the standing instruction of 2026-09-23 (keep going; leave only account-dependent steps). The decisions in section 2 were taken here and are flagged for review. Research: `korbat-scratch/research-3/{repo,threats,practice,console-lab}.md` (a repository map at 21e0ef9's code, a threat model of 38 threats with prioritised controls, a survey of the law and of moderation practice, and a laboratory measurement of the console's page under a strict Content Security Policy), every fact with its source. The draft went through an adversarial review by four critics (fit to the code, security and privacy, the SQL and the task plan, the product's promises) and was revised on 2026-09-30; their 80 findings and what was done with each are in `korbat-scratch/research-3/spec-review-3a/adjudication.md`. ## 1. Context

Sub-project 3 (trust and safety) gives moderators their powers: reports, cases, decisions, strikes, suspensions, appeals, transparency, and the two automated checks (R1 scoring, R2 hash matching). The threat model (`threats.md` T7 to T17) makes one thing come first: those powers must live somewhere an ordinary account, a bug in the public app, or a phished code cannot reach. Today the only staff guard, `requireStaffMfa` (`apps/api/src/auth/middleware.ts:87-94`), checks that the account has TOTP turned on, not that the session proved anything, and no route uses it; staff act under their ordinary session on the app's origin, whose CSRF cookie any script on the app can read (`apps/api/src/auth/cookies.ts:15`). The audit log is append-only for the API role (`packages/db/migrations/0001_grants.sql:19-20`), but only the grant-role CLI writes it, and nothing proves it cannot be changed.

This design delivers the staff side's foundation: staff keys and staff sessions on a console of its own, enrolled and revoked only from the server's command line, a per-action confirmation with the staff key, the audit log as a hash-chained record of every staff action, and the console app itself, with nothing to moderate yet. Sub-project 3c then adds cases to it, and 3d transparency and the automated checks.

| Enrolling and revoking keys | Only from the server's command line, audited: `staff.js enroll <email>` prints a one-time link to `CONSOLE_ORIGIN/enroll/<token>`, valid 30 minutes and single-use, for an account that is already staff and has a handle; the person opens it on the device that holds the key and registers it with a name. Every revocation by the command line, a demotion or a counter regression is mailed to the key's owner; an account's take-down sends only its `account_deleted` mail. | Confirming an action | A per-action **step-up**: a route that changes something asks for a fresh assertion from the session's own staff key. The action's hash is the sha256 of the sorted JSON (object keys sorted, no whitespace) of `{ action, target: { type, id }, params }`, where `params` is the route's validated request without the assertion and the target (for 3a's session revocation, `{}`). The step-up options take the same `{ action, target, params }` the route will execute, and the route recomputes the hash from what it is about to do. The challenge carries the full sha256 of the staff session's handle and the action's hash. An assertion made for one action, with other parameters or in another session, therefore confirms nothing else, and it cannot be used twice. The console checks the challenge before it asks for the key: it recomputes the action's hash from the `{ action, target, params }` it sent and the binding from its session's handle, and refuses options whose challenge binds anything else (section 9), so an API under an attacker's control cannot have the key sign an action the person did not choose. The audit row stores the action's hash, its `params` (in metadata), the key and the assertion itself (authenticator data, client data and signature). `audit-verify` checks every confirmation against the key's public key, and that the key belongs to the row's actor, without trusting the API or holding any server secret. A batch is one action of its own whose `params` list its items (3c's closing of every open report of one reporter, for example): one assertion confirms it and it writes one audit row. One assertion never confirms several separate actions. 3a uses it for revoking a staff session; 3c for every decision, reveal and evidence download. Flagged: the step-up challenge lives 10 minutes with a 5-minute prompt, as every other ceremony, not the first draft's 2 minutes; the binding and single use carry the security. Flagged: the console's check of the challenge trusts the page, which Caddy serves from its image, not the API; an attacker who can change the image or the host can change the page too. Flagged: staff key rows, public keys included, are never deleted, not even by an account's take-down, because `audit-verify` needs them for old confirmations; the take-down blanks only their names, AAGUIDs and transports (section 7). Each confirmed row stores about 460 bytes of assertion (ES256). How long the audit log keeps rows is still `threats.md` T19 and 3c's question. | A time window of freshness, as the app's re-authentication (a window lets a hidden page act several times); a hash of the action's name and target only (an assertion given for one decision on a case would confirm any other decision on it); the key and the hash without the assertion (a row naming a key would be only the API's word, `threats.md` T10); storing the sign-in assertion as well (a sign-in challenge cannot be bound to a session that does not exist yet, so it would prove only that the key signed some sign-in). |
| The record | The audit log becomes the record of every staff action: sign-ins, sign-outs, enrolments, revocations and, from 3c, every decision. Each row carries the actor, the staff session's handle, the key, the action's hash and the step-up assertion where a step-up confirmed it, the request id, its place in the chain (`chain_seq`) and a sha256 **hash chain** over the previous row's hash and the row's canonical text (section 6). A trigger that the migration role owns fills the row's id, time, place and hashes whatever the insert supplied, so the API role can neither choose where or when a row enters the chain nor change a row after (it still holds only insert and select). `staff.js audit-head` prints the newest row's place and hash for keeping off the server; `staff.js audit-verify [<place>:<hash> ...]` recomputes the whole chain in its own code, checks every stored assertion against its key, and checks every kept pair. Publishing the head is 3d's. Flagged: the chain does not stop whoever controls the database or its host: the superuser, the owner `korbat_migrate` (its password is in `infra/.env` and the migrate service uses it at every start), and anyone with Docker access on the host (psql inside the postgres container is the superuser without a password). Any of them can change a row, recompute every later hash and move the head, and a plain recompute then passes. Such a change is detected only against a head kept before it by someone other than the person who made it. Until 3d publishes the head, the staff member who does not run the server (the keeper) copies the newest place and hash from the console's audit page each day and, on the same visit, opens the place kept on the previous visit with "Go to place" and checks that it still shows the kept hash; a change that recomputes the chain changes the hash at every later place, so the newest kept place covers every row before it. After each deploy and each week the operator runs `audit-verify` with every pair the keeper has kept (runbook). A change that recomputes the chain then shows on the keeper's screen, and one that does not fails `audit-verify` for good. The keeper's check reads through the API and the page the operator deploys, so it detects a change made in the database, not one that also changes the API's code to show the kept hashes, which only 3d's publication closes; with one person, nothing detects the operator's own changes until 3d (README). A restore from backup moves the chain back too: new rows take the lost places with other hashes, so the pairs kept after the backup are retired with the restore's date (README). Flagged too: the owner may prefer 3a to mail the head each day to a second address now (`threats.md` S1) rather than wait for 3d. Flagged too: keeping the migrate password out of `infra/.env` between deploys was not adopted, because Docker access on the host already gives the superuser without a password (`pg_hba` local trust, measured); the owner may still want it as friction. | An unchained log (a changed row is undetectable); signing each row with a key the API holds (the API is what the chain protects against); an `audit-verify` that only recomputes (whoever can rewrite the rows can recompute the chain); taking the migrate password out of `infra/.env` between deploys (Docker access on the host is the superuser anyway). |
| The chain's order and times | The database alone places a row: the trigger sets its id, its time (`clock_timestamp()` truncated to milliseconds, when the row joined the chain) and its place (`chain_seq`, the order in which inserts took the head's lock), whatever the insert supplied. Every audit write holds the head until its transaction commits, so an audit row is always the last statement of its transaction (section 7). The canonical text, version 1, is written twice, in SQL for the trigger and in Node for `audit-verify`, which never asks the database for a text or a hash. `korbat_api` may read `audit_head`. Flagged: ids rise by two per row (the column's default draws one, the trigger another) and have gaps; nothing reads meaning into `id` any more, and `chain_seq` is the position. Flagged: `audit_head` keeps a single-row key. ## 5. Architecture

The auth module owns staff keys, staff sessions and enrolments (schema `auth`, role `korbat_auth`), because they are credentials. It gains a staff part (`apps/api/src/auth/staff/`): the enrolment flow, the staff sign-in flow, the staff session store and middleware (`requireStaff`, `requireStaffStepUp(action, target)`), and the step-up flow. All run through the existing WebAuthn wrapper and 1c's challenge codec, with the console's relying party ID and origin. The codec and the wrapper raise 1c's `passkey_invalid`, and the wrapper also `passkey_unsupported`; the staff flows catch both and raise a staff code in their place (section 10), so no staff answer carries a `passkey_*` code. The codec gains two purposes in its 58-byte layout, `staff_signin` (no binding) and `staff_register` (bound to the enrolment's id); its key, 10-minute lifetime and used-challenge markers stay as they are, and its binding argument becomes any string rather than only a session's handle. Step-up challenges (`staff_step_up`, bound to the staff session's handle and the action's hash) get a layout of their own in the same codec, with the same key, lifetime and markers: 74 bytes of version, purpose, expiry, nonce, the full 32-byte binding and the 16-byte seal, so `audit-verify` can recompute the binding from a stored assertion without the sealing key (section 7) and the console can check it before it asks for the key (section 9); the layout's offsets and the purpose's code are in the contracts, which the codec, `audit-verify` and the console read. The wrapper's `registrationOptions` and `authenticationOptions` gain a `userVerification` argument: `"preferred"` for 1c's callers and `"required"` for every staff ceremony. `registrationOptions` also gains an optional security-key hint, passed to the library as `preferredAuthenticatorType: "securityKey"`, and `verifyAuthentication` also reports the BE flag. Verification keeps `requireUserVerification: false`. The staff flows refuse on the reported flags after the library has verified, so each refusal has its own code.

A new module, `apps/api/src/staff/` (role `korbat_api`), owns the audit reader, `chain.ts` (the canonical text in Node, section 6) and the writer for actions on public tables (3c is its first user; the auth module writes auth-side rows through `auth.append_audit`), and mounts the staff routes at `/api/staff/*`, using the auth module's interface as the other modules do (`createAuth` exposes `requireStaff`, `requireStaffStepUp` and the staff flows). `createApp` mounts the staff routes with the other modules, after the global rate limit, and only while `CONSOLE_ORIGIN` is set. It passes the app's CORS and `resolveSession` over every path that is `/api/staff` or begins with `/api/staff/`, with one path test, as it already passes the upload route over the JSON body limit (`apps/api/src/app.ts:48`). The staff routes so keep the request id and access log, the client identity, the API's security headers and `no-store`, the 64 KiB body limit and the global rate limit, and never meet the app's CORS, its Origin allow-list, its session or its CSRF check: the staff gate and `requireStaff` (section 7) are their only origin and session logic. Without the skip, `resolveSession` would answer every console POST 403 `csrf_failed`, since its allow-list is `APP_ORIGIN` and `TRUSTED_ORIGINS` (`apps/api/src/auth/middleware.ts:20-24`, `apps/api/src/auth/context.ts:40`), and the app's credentialed CORS (`app.ts:43`) would answer staff reads for every trusted origin. Listing the console in `TRUSTED_ORIGINS` is not a way round it, and the configuration refuses it (section 8).

The auth module keeps the credential parts of the staff routes. It raises every staff error code as an `AuthError` (section 10). Its index exports `setStaffCookies` and `clearStaffCookies` (`auth/staff/cookies.ts`), which the staff module's sign-in and sign-out routes call, as it already exports `clearSessionCookies` to the account module. The staff cookies' names and attributes stay the auth module's, and `requireStaff` is their only reader. The staff module raises no code of its own; a malformed request is 400 `invalid_request`, as elsewhere. The architecture test's module list gains `staff`, with two rules of its own. First, inside `staff/`, no auth-schema table or enum is imported from `@korbat/db`, as for the social and media modules. Second, neither `createAuthRepo` nor `createSessions` is imported from the auth module. `cli/staff.ts` joins `config.ts`, `index.ts` and `cli/grant-role.ts` in `AUTH_POOL_ALLOWED`, since it opens both pools as grant-role does. Each new rule has a test that catches a deliberate violation, as the existing rules have. The command line `apps/api/src/cli/staff.ts` (built as `dist/staff.js` beside `dist/grant-role.js`, from an entry in `apps/api/build.mjs`) enrols (run in the migrate service, as the migrator), lists and revokes keys, reads the audit head and verifies the record. The console is `apps/admin`: React, esbuild and CSS, built into Caddy's image like the app's export and served by Caddy's second site.

## 6. Data model (migration 0012)

- `auth.staff_keys`: `id uuid` primary key, `user_id` references `auth.users` on delete restrict (below), `credential_id text` unique, `public_key text`, `counter bigint`, `transports text[]`, `name text`, `aaguid uuid null`, `origin text` and `rp_id text` (the console's origin and relying party ID the key was enrolled for, copied from its enrolment), `created_at`, `last_used_at null`, `revoked_at null`, `suspect_at null` (set together with `revoked_at` when a counter goes backwards, section 7: a suspect staff key is a revoked key whose record says why), and a unique (`id`, `user_id`) that the staff sessions' foreign key names. A key is live while `revoked_at` is null; `suspect_at` is never set without it. Only keys whose registration reported UV and no BE exist; the flow refuses the others before the insert. A key has no user handle of its own: staff registrations use the account's `auth.users.webauthn_user_id` (1c's random 32 bytes, never the account id). A staff key row is never deleted: revocation and an account's take-down set `revoked_at`, because `audit-verify` checks old confirmations against its public key, owner, origin and relying party ID. The migration revokes what 0001's default privileges grant, as 0003 does. `korbat_auth` keeps SELECT and UPDATE of `counter`, `last_used_at`, `revoked_at` and `suspect_at` only, and a `before update` trigger refuses to clear or change a set `revoked_at` or `suspect_at`. Keys are inserted only by `auth.add_staff_key(token, credential_id, public_key, counter, transports, name, aaguid, request_id)`. This is a migrator-owned `security definer` function with its `search_path` pinned to `auth, pg_temp` (`public.audit_log` named in full), EXECUTE revoked from PUBLIC and granted to `korbat_auth`. It hashes the token itself, so a token hash read from the table spends nothing. In the caller's transaction it spends the matching enrolment only if the enrolment is unused and unexpired. It checks, under a `FOR NO KEY UPDATE` lock on the account's row (section 7), that the account is live and staff, has a handle, and holds fewer than five live keys. It then inserts the key, with the origin and relying party ID its enrolment recorded, and writes its `staff_key_added` audit row, which names the key in `key_id` and as its target (`target_type` `staff_key`). `auth.forget_staff_keys(user_id)` is a migrator-owned function of the same kind (`security definer`, the same `search_path`, EXECUTE revoked from PUBLIC and granted to `korbat_auth`). For an account marked deleted it sets every staff key's `name` to an empty string, `aaguid` to null and `transports` to an empty array; for a live account it changes nothing. The take-down calls it (section 7), so a deleted account's keys keep no name, AAGUID or transports: only what `audit-verify` needs (the id, the owner, the credential id, the public key, the origin and the relying party ID), their counter and their dates.
- `auth.staff_enrollments`: `id uuid`, `user_id` references `auth.users` on delete cascade, `token_hash text` unique, `origin text` and `rp_id text` (`CONSOLE_ORIGIN` and the console's relying party ID when `staff.js enroll` issued it), `created_at`, `expires_at`, `used_at null`. The link's token is 32 random bytes; only its sha256 is kept. `korbat_auth` holds SELECT and DELETE only: it cancels an open enrolment by deleting it (a role change, `revoke ... all`, the take-down), and the janitor deletes spent ones. The same never-cleared trigger, on this table, refuses to clear a set `used_at`. Enrolments are inserted only by `staff.js enroll` as the migrator and spent only by `auth.add_staff_key`.
- `auth.staff_sessions`: `id text` primary key (the token's sha256), `handle uuid` unique, `user_id` references `auth.users` on delete cascade, `key_id`, with (`key_id`, `user_id`) referencing `auth.staff_keys (id, user_id)` on delete cascade, so a session's key always belongs to its account whoever writes the row, `created_at`, `last_used_at` (the time of the person's last action, section 7), `idle_expires_at`, `absolute_expires_at`, `revoked_at null`, `browser text` (the coarse label that `deviceLabel(userAgent, "web")` gives (`apps/api/src/auth/devices.ts:7`), such as "Firefox on Linux"; shown in the session list and the sign-in mail; never the user agent itself, never an IP). A check keeps `absolute_expires_at` at most 12 hours after `created_at` and `idle_expires_at` at most `absolute_expires_at`. `requireStaff` refuses a session whose `created_at` is later than now. A session row written behind the flows' back therefore ends within 12 hours.
- Accounts are never deleted by korbat, only marked deleted and anonymised (`apps/api/src/auth/repo.ts:226-284`), so the `on delete cascade` of `user_id` never fires, and staff keys are never deleted, so neither does the sessions' cascade from their key; the take-down and the janitor act on staff rows by name (section 7, Role changes, deletion and retention). The development cleaner does delete test accounts, as the superuser (`scripts/clean-dev-fixtures.mjs:112`); `staff_keys.user_id` is therefore `on delete restrict` and the cleaner skips an account that holds a staff key, so no delete takes a key with it and `audit-verify` keeps every public key it needs.
- `auth.auth_event_type` gains `staff_enrollment_issued`, `staff_key_added`, `staff_key_revoked`, `staff_key_counter_regression`, `staff_sign_in`, `staff_signed_out`, `staff_session_revoked`.
- `public.audit_log` gains `staff_session uuid null` (the session's handle), `key_id uuid null`, `action_hash text null`, `step_up jsonb null` (the assertion's `authenticatorData`, `clientDataJSON` and `signature`, base64url exactly as the browser sent them), with a check that `action_hash` and `step_up` are both null or both set and that `key_id` is set when they are, and four chain columns, each NOT NULL with a placeholder default that the trigger always overwrites: `chain_version smallint default 0`, `chain_seq bigint default 0`, `prev_hash text default ''`, `hash text default ''`. The placeholders keep drizzle's insert type from requiring them (the staff module's writer supplies none of them) and let `ADD COLUMN` succeed over the rows the development and test databases already hold. A unique index on `chain_seq` serves the viewer and `audit-verify`; there is no `(created_at desc, id desc)` index.
- `public.audit_head (id smallint primary key check (id = 1), seq bigint not null, hash text not null)` holds one row: the place and hash of the newest row, `(1, 0, 64 zeros)` for an empty log. It is declared in `safety.ts` with RLS and one policy, `audit_head_api_select`, FOR SELECT TO `korbat_api`. The migration revokes everything the default privileges of `0001_grants.sql:16` give `korbat_api` on it and grants SELECT back, so `korbat_api` reads the head and can neither write it nor lock it (SELECT ... FOR UPDATE needs UPDATE). On `audit_log` it keeps INSERT and SELECT; UPDATE, DELETE and TRUNCATE stay revoked (`0001_grants.sql:20`).
- The trigger `audit_chain`, BEFORE INSERT FOR EACH ROW, runs `public.audit_chain()`: SECURITY DEFINER, owned by `korbat_migrate`, created with `SET search_path = public, pg_temp` as `0007` pins `auth, pg_temp`, with every object named schema-qualified, so no temporary table can stand in for the head; EXECUTE on it is revoked from PUBLIC (the trigger still fires for `korbat_api`). It locks the head row with SELECT ... FOR UPDATE and raises `the audit head is missing` when there is none, never creating one. It then sets, ignoring whatever the insert supplied: `id` to `nextval('public.audit_log_id_seq')`, so an insert naming an existing id with `ON CONFLICT DO NOTHING` cannot move the head without writing its row; `created_at` to `clock_timestamp()` truncated to milliseconds, the time the row joined the chain; `chain_version` to 1; `chain_seq` to the head's `seq` + 1; `prev_hash` to the head's hash; and `hash` to the lower-case hex sha256 of the UTF-8 bytes of `prev_hash` followed by the row's canonical text (`encode(sha256(convert_to(..., 'UTF8')), 'hex')`, never a cast to bytea, which reads backslashes as escapes). Last it moves the head to the row's `chain_seq` and `hash`. The chain's order is `chain_seq`, the order in which inserts took the head's lock; it has no gaps, since a rolled-back insert rolls the head back with it. The lock lasts until the inserting transaction ends (section 7).
- **The canonical text, version 1**, is defined here and nowhere else, and implemented twice: in SQL by `public.audit_chain_text(r public.audit_log)` (plpgsql, the same `search_path`, EXECUTE revoked from PUBLIC), which the trigger and the back-fill call; and in Node by the staff module's `chain.ts`, which `audit-verify` calls and which never asks the database to compute a text or a hash, since the owner can replace the database's functions. It is a JSON array with no whitespace between its elements, in this order: `chain_version`, `chain_seq` and `id` as decimal integers; `created_at` in UTC as a JSON string of the form `YYYY-MM-DDTHH:MM:SS.mmmZ` (in SQL `to_char(created_at at time zone 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')`, in Node `toISOString()`); `actor_id`, `action`, `target_type`, `target_id`, `request_id`, `staff_session`, `key_id` and `action_hash`, each a JSON string (uuids in PostgreSQL's lower-case form) or `null` when the column is null; then `step_up` and last `metadata`, each exactly as PostgreSQL prints the stored jsonb (`::text`: jsonb's own key order, `", "` and `": "` separators), or `null` when `step_up` is null, which the verifier reads with that cast and never re-serialises. Strings are escaped as `to_json(text)` and `JSON.stringify` escape them, which agree. The SQL function raises on a version it does not know and `chain.ts` refuses one; a later sub-project that adds a chained column adds version 2 to both, and every row keeps the version it was written with.
- `auth.append_audit(actor_id, action, target_type, target_id, metadata, staff_session, key_id, action_hash, step_up, request_id)` is owned by the migrator: `security definer`, `search_path` pinned to `auth, pg_temp`, `public.audit_log` named in full, EXECUTE revoked from PUBLIC and granted to `korbat_auth` only. It refuses any action outside the auth side's list: `staff_key_revoked`, `staff_key_counter_regression`, `staff_sign_in`, `staff_signed_out`, `staff_session_revoked`, `staff_enrollments_cancelled` and `role_granted` (the take-down's revocations are `staff_key_revoked` rows). The auth flows call it as the last statement of their transaction.
- Migration 0012 is generated and then completed by hand in the same file, as `0009` is. Generated: the enum values, the auth tables with their checks, `audit_log`'s new columns with their placeholder defaults and its check, `audit_head` and the policies, with the unique index on `chain_seq` moved below the back-fill (created before it, it fails on the placeholder zeros). Hand-written, in this order: `audit_chain_text`; the existing rows' `created_at` truncated to milliseconds; the back-fill, which chains the existing rows in id order with `chain_version` 1, `chain_seq` from 1 and `prev_hash` from 64 zeros; the head row set to the last row's place and hash; the unique index; the REVOKE and GRANT on `audit_head`; `audit_chain` with EXECUTE revoked from PUBLIC; the trigger; then the auth side: the REVOKE and GRANT on the staff tables, their never-cleared trigger, and `auth.add_staff_key`, `auth.append_audit` and `auth.forget_staff_keys` with EXECUTE revoked from PUBLIC and granted to `korbat_auth`. drizzle's migrator runs it in one transaction, so a failure leaves nothing half-chained, and the generate gate still prints No schema changes.
- RLS on every new table with one policy: the auth tables' for `korbat_auth`; `audit_head`'s, SELECT only, for `korbat_api` (its owner, which the trigger runs as, bypasses RLS).

## 7. Flows

- **Enrolment.** `staff.js enroll <email>` runs in the migrate service as the migrator, needing only `DATABASE_URL_MIGRATE`, `CONSOLE_ORIGIN` and `CONSOLE_RP_ID`, which Compose gives that service. It refuses while `CONSOLE_ORIGIN` is unset, with a message naming it, and writes nothing. It refuses unless the account is live, staff and has a handle, and refuses an account that already has 5 live keys. It writes the enrolment, with `CONSOLE_ORIGIN` and the console's relying party ID recorded on it, the `staff_enrollment_issued` auth event and its audit row (system actor) in one transaction, and prints the link. The console's enrolment page asks for the key's name and its kind, then asks the API for registration options (`POST /api/staff/enroll/options { token, name, kind }`, where `kind` is `security_key` or `this_device`). The token must be unused and unexpired, and the account still live, staff and with a handle; otherwise the answer is `staff_enrollment_invalid`, as it is for an enrolment whose recorded origin or relying party ID is not the running configuration's (the console moved after the link was issued). The user handle is the account's `users.webauthn_user_id`, set now with 1c's compare-and-set (`ensureWebauthnUserId`) when the account has none. `user.name` and `user.displayName` are the key's name, never the email, the handle or the account id. The options name the console's relying party and require user verification and a resident key. They exclude the account's existing staff keys, and also its personal passkeys while `CONSOLE_RP_ID` equals the app's relying party ID (development), and 1c's registration options then exclude its live staff keys in the same way (section 2); and they pin the algorithms 1c pins. They carry the security-key hint when `kind` is `security_key` and no hint otherwise, and a `staff_register` challenge bound to the enrolment's id. `POST /api/staff/enroll/verify { token, name, response }` finds the enrolment by its token (`staff_enrollment_invalid` as above), reads the challenge against the enrolment's id and spends it, then verifies against `CONSOLE_ORIGIN` and `CONSOLE_RP_ID`. A challenge the codec refuses (forged, of another purpose, bound to another enrolment or spent), a response the library refuses and an attestation the wrapper does not accept are all `staff_key_refused`. It refuses a key whose registration did not report UV (`staff_key_not_user_verified`) or reported BE (`staff_key_not_device_bound`). A refusal leaves the link usable until it expires, so the person can try again with another key. Otherwise it does its whole write in one transaction on the auth role. The transaction first locks the account's row `FOR NO KEY UPDATE` (as the take-down and 1c's registration take it first; the lock's mode is under Command line below), writes the `staff_key_added` auth event, and last calls `auth.add_staff_key`, which re-checks under that lock that the account is live, staff and has a handle, that the enrolment still exists unused and unexpired, and that the account holds fewer than five live keys, then spends the token, stores the key with the AAGUID it reported and the origin and relying party ID the enrolment recorded, and writes its audit row. After the commit the owner is mailed `staff_key_added`. A link issued before a `revoke ... all`, a role change or a deletion therefore enrols nothing. At most 5 live keys per person: `staff.js enroll` refuses an account that already has 5, and the verify step refuses a sixth with `staff_key_limit` (when two links were issued at once).
- **Sign-in.** `POST /api/staff/signin/options` takes no body and answers with a `staff_signin` challenge, discoverable credentials, an empty allow list and user verification required. `POST /api/staff/signin/verify { response }` reads the challenge and spends it first. The credential must be a live staff key of a live staff account. The response's user handle must be present and equal to that account's `webauthn_user_id`, because the allow list named no one (as in 1c's `signInVerify`). Every failure up to here gets one answer: a challenge the codec refuses (forged, of another purpose or spent), an unknown or revoked key, an account that is no longer live or staff, and a missing or wrong user handle are all refused with `staff_key_invalid`. The library then verifies the signature, the origin `CONSOLE_ORIGIN` and the relying party ID, and a response it refuses is `staff_key_invalid` as well, so no answer tells a live key from a revoked or unknown one. After that the flow refuses an assertion that does not report UV (`staff_key_not_user_verified`) or that reports BE or BS (`staff_key_not_device_bound`; WebAuthn L3 asks a relying party that uses BE in policy to check it on every assertion), and it applies the counter rule: a regression, found only after the signature verifies, is refused with `staff_key_suspended` (below). It creates a staff session whose `browser` is `deviceLabel(userAgent, "web")`, sets the two cookies, writes `staff_sign_in` and its audit row in the session's transaction, and mails the owner `staff_session_started` with the key's name, the browser label and the time. Limits: per IP, 20 attempts an hour, counted before anything else. Per key, 10 an hour, counted only after the signature and the flags have checked, as 1c counts its new-device limit (`flows.ts:383-386`), so only the key's holder can spend it and an unsigned response naming a key's credential id cannot lock its owner out.
- **A counter that goes backwards.** Every staff assertion, at sign-in and at step-up, runs 1c's counter rule (`isCounterRegression`, one conditional update) after its signature has verified. A regression revokes the key. In one transaction on the auth role `suspect_at` and `revoked_at` are set, every live staff session the key opened is revoked, `staff_key_counter_regression` is appended, and its audit row is written through `auth.append_audit`, last. Then the owner is mailed `staff_key_suspect` (never 1c's `passkey_suspect`, whose remedy names the app's Security screen), and the attempt is refused with `staff_key_suspended`. It is the routine `staff.js revoke` runs, with `suspect_at` set as well and the regression's own event; a suspect key opens and confirms nothing more, and only the command line enrols a replacement.
- **The staff gate.** Every request under `/api/staff/`, with or without a session (sign-in and enrolment included), first passes one gate, before any flow runs or any session is read. Its `Host` header, port included, must equal `new URL(CONSOLE_ORIGIN).host`; otherwise it is answered 404 `not_found`, as on the app's site. The API reads `Host`, which Caddy and cloudflared pass on unchanged, never `X-Forwarded-Host`, and the integration harness sets `Host` itself, since an in-process request has none. An `Origin` header, when present, must be exactly `CONSOLE_ORIGIN`, and it must be present on anything but GET and HEAD. A `Sec-Fetch-Site` header, when present, must be `same-origin`; the API already reads fetch metadata (`apps/api/src/auth/routes.ts:61-67`). A request that fails the Origin or `Sec-Fetch-Site` test is answered 403 `csrf_failed` and touches no session, so a page on another origin of the same site (the app on a subdomain, or any localhost port in development) can neither act nor keep a staff session from going idle. Staff answers carry no CORS headers: the console calls its API on its own origin.
- **Every staff request.** `requireStaff` reads only the staff cookie (never a bearer token, never the app's session cookie) and, for anything but GET and HEAD, requires the `x-staff-csrf` header to equal the staff CSRF cookie. It reads the session from the database on every request, never from a cache: one indexed read joined to the key and the account, so a revocation, a demotion, a deletion or a suspect key ends the session at its next request with no tombstone. The session must be unrevoked and before its idle and absolute expiries, its key unrevoked, and its account live and still staff; otherwise the answer is 401 `staff_session_required`, which also clears both staff cookies (the console then shows sign-in). The idle expiry counts the person's actions, not requests: the console sends `X-Staff-Activity: 1` on each request a person's action starts (a click, a submitted form, opening a screen), and only such a request moves `last_used_at` to now and the idle expiry to the earlier of now plus 15 minutes and the absolute expiry, in the same statement that reads the session. A request without the header is checked the same way and moves nothing, so a page left open cannot keep its session alive by itself. The header governs the console's own requests; it is no defence against a script in the page, which the policy of section 8 and the step-up answer. Both staff cookies are set at sign-in with a Max-Age of 12 hours, the absolute limit, and are never refreshed; the server enforces the idle limit. Staff routes answer `Cache-Control: no-store` like every API answer.
- **Step-up.** `POST /api/staff/step-up/options { action, target, params }`: the action must be one of the contracts' step-up actions (`STAFF_STEP_UP_ACTIONS`; in 3a, `staff_session_revoked`), and `target` and `params` are validated with that action's own schema. The action's hash is the lower-case hex sha256 of the sorted JSON (object keys sorted, no whitespace) of `{ action, target: { type, id }, params }`. The answer carries a sealed `staff_step_up` challenge (the 1c pattern: an HMAC seal over its fields and an expiry, in the layout of section 5) whose binding is the full 32-byte sha256 of the session's handle, a newline and the action's hash, not a 16-byte prefix; the console checks that binding before it asks for the key (section 9). The options require user verification, and their allow list holds only the session's key. The challenge lives 10 minutes and the browser's prompt 5, as in every other ceremony (WebAuthn L3 recommends a timeout of 5 to 10 minutes). Single use and the binding, not a short life, keep an assertion from confirming anything else. The action route takes its own body with `stepUp: <assertion>` added. `requireStaffStepUp(action, target)` reads the route's own target from the request through its `target` function (for `DELETE /api/staff/sessions/:handle`, the path's handle), takes the params the route validated and will execute, and recomputes the action's hash from them. It reads the challenge against the session's handle and that hash (its seal, expiry and binding), then spends it (a used-challenge marker in Valkey until the expiry). It checks that the assertion's credential is the session's key and verifies it, refuses an assertion that does not report UV or reports BE or BS, and runs the counter rule (a regression as at sign-in). A challenge the codec refuses (forged, of another purpose, bound to another session, action, target or params, or spent), an assertion from another key and one the library refuses are all `staff_step_up_invalid`. The route's audit row, written in the same transaction as the action (through `auth.append_audit` when the action changes an auth table, as 3a's revocation does), stores the action's hash, `metadata.params`, the key and the assertion in `step_up`.
- **Sessions and keys.** `GET /api/staff/me` (the account's handle, role, the session's handle, and the session's idle and absolute expiries, each with the seconds left, so the console needs no clock of its own); `GET /api/staff/sessions` (the person's live staff sessions: browser, created, last used, this one); `DELETE /api/staff/sessions/:handle` with step-up (revokes one of the person's own staff sessions; its `staff_session_revoked` event and audit row); `POST /api/staff/signout` (ends this session; no step-up; `staff_signed_out` and its audit row); `GET /api/staff/keys` (the person's keys: name, created, last used; never the public key). `GET /api/staff/audit?action=staff_sign_in` (the audit reader's one filter) feeds the home screen's list of every staff account's sign-ins in the last 7 days; the console reads its pages until it reaches a sign-in older than 7 days. No route adds or revokes a key: keys are added through the command line's enrolments and revoked by the command line, a counter regression or an account's take-down.
- **The audit log.** `GET /api/staff/audit?cursor=` (any staff member; newest first by `chain_seq`, 50 a page, the cursor a `chain_seq`; `?at=<chain_seq>` answers the page whose newest row is at that place, which the keeper's check opens (section 2); each row: time, actor handle, action, target type and id, the action's hash, and its place and hash in the chain; never metadata that names an email, IP, device or phone, which the writer never stores). Reading is not itself recorded.
- **Command line.** `staff.js enroll|keys|revoke|audit-head|audit-verify`. `enroll` runs in the migrate service as the migrator; the others run like grant-role (`docker compose ... run --rm api node dist/staff.js ...`). `staff.js keys <email>` lists that account's keys (id, name, reported AAGUID, created, last used, revoked, suspect); without an email it lists every account whose role is not `user`, with its role, address, handle and keys, for the runbook's comparison with the operator's own list. `staff.js revoke <email> <key id>` revokes that key and every staff session it opened; `staff.js revoke <email> all` revokes every key and every staff session of the account and deletes its unused enrolments. Both run in one auth transaction that first locks the account's row and appends `staff_key_revoked` for each key revoked (metadata: the key's id, the count of staff sessions revoked, `via: "cli"`) with its audit row; `revoke ... all` also writes one `staff_enrollments_cancelled` row (the count, `via: "cli"`) when it deleted an unused enrolment, so it never changes the database without a row. After the commit the owner is mailed `staff_keys_revoked` when a key was revoked; an enrolment cancelled alone sends no mail, as with grant-role. The command line builds the mailer as the API does (`SMTP_URL`, `MAIL_FROM`); a mail that fails is printed as a warning and undoes nothing. Grant-role builds the same mailer for a demotion's `staff_keys_revoked`. Every writing command writes its audit row in the same transaction as its change: directly when running as the migrator, through `auth.append_audit` on the auth role. An audit row is always the last statement of its transaction: the head's lock lasts until commit, so nothing that can wait (another row lock, Valkey, a mail, a WebAuthn check) runs between the insert and the commit. A transaction that wrote its audit row first and then waited for a row another audit writer held would deadlock with it. Every transaction that locks an account's row before its other statements (enrolment and `auth.add_staff_key`, `staff.js revoke`, the counter regression) takes it `FOR NO KEY UPDATE`, the lock that grant-role's and the take-down's updates of that row take. These still wait for each other, but the `FOR KEY SHARE` lock that an insert into `auth_events` or `staff_sessions` takes on the account's row through its foreign key does not wait for them. Taken `FOR UPDATE`, a revocation holding the account's row and waiting for a staff session's row would deadlock with a sign-out holding that session's row and inserting its event. `staff.js` and grant-role set `lock_timeout` to 10 seconds; a command that times out has written nothing, and says that an open transaction holds the audit head or the account's row and that the api service should be stopped before the command is run again. Grant-role's role change and its `role_granted` row become one transaction the same way (below), and it no longer writes the audit log on the API's pool. `staff.js audit-head` prints the newest row's `chain_seq`, hash and time, reading the newest row and `audit_head` in one statement and checking that the head names that row. `staff.js audit-verify [<chain_seq>:<hash> ...]` opens its own connection on the API's role with `DateStyle` ISO and `TimeZone` UTC and, in one `REPEATABLE READ READ ONLY` transaction, reads the head and every row up to the head's place in `chain_seq` order a page at a time, so a row written meanwhile is neither read nor missed. It then reads the staff keys (id, owner, public key, origin and relying party ID) from `auth.staff_keys` on the auth role; a key whose `staff_key_added` row is not among the rows read is looked up again, and one whose row was written after the head it read is left to the next run. It fails (exit 1, naming the first rows at fault) unless all of these hold: `chain_seq` runs from 1 without a gap; the first `prev_hash` is 64 zeros; every `prev_hash` is the previous row's hash; every hash matches the text `chain.ts` recomputes; `audit_head` names the newest row; every kept pair still names a row with that hash; every row with a step-up passes the checks below; every row whose action is in `STAFF_STEP_UP_ACTIONS` carries a step-up, whatever its actor; and every staff key has exactly one `staff_key_added` row, which names it in `key_id`. For every row with a step-up it recomputes the action's hash from the row's action, target and `metadata.params`; checks that the challenge in the client data carries the sha256 of the row's session handle and that hash, and had not expired when the row was written; checks that the key named by `key_id` belongs to the row's `actor_id`; checks that the client data is a `webauthn.get` for the origin recorded on the key and that the authenticator data names the relying party ID recorded on the key with user presence and verification; checks that the signature verifies with the key's public key; and checks that no challenge appears in two rows. It also reports how many rows follow the newest kept pair and are not yet anchored. It needs no server secret and no console configuration, so it runs the same with the console off or moved.
- **Role changes, deletion and retention.** `grantRole` (`apps/api/src/auth/admin.ts`) runs in one transaction on the auth role, starting with the role's update, which locks the account's row: it sets the role, revokes every session and every staff session, and deletes every unused enrolment. When the new role is `user` it also revokes every staff key and appends `staff_key_revoked` for each (`via: "role_change"`). Its last statements write, through `auth.append_audit`, the audit row of each `staff_key_revoked` and the `role_granted` row, whose metadata gains the counts of staff sessions revoked and enrolments deleted. After the commit the app sessions get their tombstones as today, and the owner is mailed `staff_keys_revoked` when a key was revoked. The account take-down (`takeDownRows`, `apps/api/src/auth/repo.ts:806`, which `finishTakeDown` runs again) also revokes the account's live staff keys and staff sessions, appending `staff_key_revoked` for each key (`via: "take_down"`), deletes its enrolments, and blanks its staff keys' names, AAGUIDs and transports through `auth.forget_staff_keys`, in the same transaction. `takeDownRows` writes no audit row: it returns the keys it revoked and the count of enrolments it deleted. `takeDown` after its `account_deleted` event (`repo.ts:229-230`), and `finishTakeDown` after `takeDownRows`, write through `auth.append_audit`, as their last statements, the audit row of each `staff_key_revoked` and, when an enrolment went, one `staff_enrollments_cancelled` row (the count, `via: "take_down"`). A deleted account keeps no live staff credential, as it keeps no passkey; its staff keys stay, revoked and without their names, AAGUIDs and transports, because `audit-verify` checks old confirmations against them. The staff sessions need no tombstone because they are never cached. The auth janitor (`apps/api/src/auth/janitor.ts`) deletes staff sessions 30 days after they were revoked or expired, as it deletes sessions, and enrolments a day after they were used or expired, as it deletes email codes; it never touches a live one. Staff keys are never deleted (audit rows name them by id). Staff auth events go after 90 days with every auth event; their audit rows stay.
- **Staff mails.** Four templates join the closed union (`apps/api/src/mail/mailer.ts`). They are plain paragraphs like the others, sent best effort through `notifyAccount` to the staff account's address, with times printed as 1c's mails print them. None carries a link, and each ends with 'korbat never puts a link in a staff email.' `staff_key_added` {name, time}: subject 'A staff key was added to your korbat staff account'; 'A staff key named "{name}" was registered for your korbat staff account at {time}. It can open the staff console.' 'If this was you, there is nothing to do. If not, tell the operator at once; they revoke the key with the staff command line.' `staff_session_started` {name, browser, time}: subject 'A staff session started on the korbat console'; 'A staff session was started on the korbat console at {time} with your staff key "{name}", from {browser}.' 'If this was you, there is nothing to do. If not, someone holds that key: tell the operator at once; they revoke it and every session it opened with the staff command line.' `staff_key_suspect` {name}: subject 'A staff key on your korbat staff account was switched off'; 'A use of your staff key "{name}" on the korbat console (a sign-in or a confirmation) looked like a copy of it, so korbat switched that key off and ended every staff session it opened. It can no longer open the console.' 'Ask the operator for a link to register a new key. If you did not use it just now, tell them so: someone else holds a copy of the key.' `staff_keys_revoked` {names, time}: subject 'Staff keys revoked on your korbat staff account'; 'These staff keys of your korbat staff account were revoked at {time}: {names}. They can no longer open the console, and every staff session they opened has ended.' 'If you expected this, there is nothing to do. If not, ask the operator why.' No mail is sent when someone signs out, revokes one of their own sessions in the console, or changes a role in a way that revokes no key, and an account's take-down sends only its `account_deleted` mail.

## 8. Origins, hosts and headers

- `CONSOLE_ORIGIN` is read like `WEBAUTHN_RP_ID`: a blank value counts as unset, since Compose passes an empty line of `infra/.env` as an empty string. Unset, the console is off: the staff routes are not mounted, every path under `/api/staff/` answers 404 on either site, and `staff.js enroll` refuses. Caddy's console site is always built and always serves the page, which says that the console is not available at this address (section 9) when `GET /api/staff/me` answers 404; the API is the only switch, and no tunnel hostname reaches the site until the operator adds one. In every environment `CONSOLE_ORIGIN` must not equal `APP_ORIGIN` and must not appear in `TRUSTED_ORIGINS`. Listing it there would make it an allowed Origin for the app's cookie-authenticated writes, a credentialed CORS origin of the app's API and, outside production, an accepted origin for personal passkeys (`apps/api/src/auth/context.ts:40,53`). In production it must be https. Its hostname must differ from `APP_ORIGIN`'s hostname, because ports do not separate sites or cookies. `APP_ORIGIN`'s hostname must not be a subdomain of it either, since a console on a parent domain of the app would let the app's pages ask for staff keys. `CONSOLE_RP_ID` defaults to the console's hostname. In production it must equal that hostname and differ from the app's relying party ID, so staff keys work on the console and nowhere else. These relying-party rules apply in production only, as the app's do (`apps/api/src/config.ts:131`).
- Caddy's console site listens on port 8090 in the container (the image also `EXPOSE`s 8090). The development override publishes it on `127.0.0.1:${DEV_CONSOLE_PORT:-8090}`, and `CONSOLE_ORIGIN` must name the same port on localhost. The site proxies `/api/staff` and `/api/staff/*` to `api:3000` as the app's site proxies `/api/*`: `request_body` at 64KB, `header -Server`, and `import /etc/caddy/cf-header.caddy` inside `reverse_proxy`, so a client-set `CF-Connecting-IP` is dropped unless `TUNNEL=on` (the per-IP sign-in limits key on it). It sets no `header_up Host`, so the API sees the Host the browser sent. Caddy's own handling of `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host`, which replaces what an untrusted client sent, is kept. Any other `/api/*` is answered 404. Everything else is served from the console's static files, with `index.html` as the fallback and `encode gzip`. They live in a directory outside the app's root (`/console`, not under `/srv`), so the app's site can never serve them. Its headers: the CSP of section 3 exactly, `Strict-Transport-Security`, `X-Content-Type-Options nosniff`, `X-Frame-Options DENY`, `Referrer-Policy no-referrer`, `Cross-Origin-Opener-Policy same-origin`, `Cross-Origin-Resource-Policy same-origin`, `Permissions-Policy` denying camera, microphone and geolocation and allowing `publickey-credentials-get` and `publickey-credentials-create` to the console itself only, `Cache-Control: no-store, no-transform` on the page (every answer that is not a hashed bundle file), and `public, max-age=31536000, immutable` on the hashed files. `no-transform` stops Cloudflare injecting its JavaScript Detections script, which Bot Fight Mode turns on for a whole zone and which cannot be turned off, and its automatic Web Analytics beacon. The CSP would block either on every page view. The app's site answers `/api/staff` and `/api/staff/*` with 404, ahead of its API proxy.
- In development both origins are on localhost: the app at `http://localhost:8080` through Caddy or `http://localhost:8081` from Expo's dev server, the console at `http://localhost:8090`. Browsers send each origin's cookies to every port of localhost, so the app's cookies reach the console's port and the staff cookies reach the app's. Four things keep the two apart: the separate cookie names, the staff gate (Host, Origin and `Sec-Fetch-Site`), the staff CSRF header and the absence of CORS on staff routes. Both relying party IDs are `localhost` there, so a browser offers personal passkeys at the console's sign-in and staff keys at the app's, and only the tables refuse them. The console is opened at `http://localhost:<port>`, never `127.0.0.1`, because browsers refuse WebAuthn on an IP address. In production the hostnames differ.

## 9. The console app (`apps/admin`)

React function components, a small router of its own (four paths: `/signin`, `/enroll/:token`, `/`, `/audit`), `fetch` wrappers that send the CSRF header and parse every answer with the contracts' zod schemas (jitless), one CSS file. Every user-written string (handles, key names, browser names) renders as a text node; no `dangerouslySetInnerHTML`, no `innerHTML`, no links built from data.

Screens: sign-in ("Sign in with your staff key", the browser's prompt, errors in the words of section 10); home (signed in as, role, the staff sign-ins of every staff account in the last 7 days (time and handle, newest first, read page by page until a sign-in older than 7 days), the session's absolute end ("Signed in until 21:40"), the person's staff sessions with "Sign out that session" confirmed by the key, the person's keys); the audit log (a table, newest first, "Load older", and "Go to place", which opens the page at a place the keeper kept); "Cases arrive in sub-project 3c." When `GET /api/staff/me` answers 404, the console shows only "The staff console is not available at this address. It is off on this server, or this is not the address set in CONSOLE_ORIGIN: open it at exactly that address, never at 127.0.0.1." The staff gate answers a wrong Host with the same 404 as a console that is off, so the page cannot tell the two apart.

Before it asks for the key to confirm an action, the console checks the step-up options it was given. The challenge must be the 74 bytes of the step-up layout (the contracts' offsets) with the `staff_step_up` purpose, its binding must equal the sha256 of the session's handle (from `GET /api/staff/me`), a newline and the action's hash that the page computes with WebCrypto from the `{ action, target, params }` it sent, and the allow list must hold one key. Otherwise the page does not call `navigator.credentials.get` and says the confirmation could not be checked. So an API under an attacker's control cannot have the key sign an action the person did not choose; the check trusts the page, which Caddy serves from its image, not the API.

Enrolment. Before the ceremony the page says which keys work: a security key with a PIN, or Windows Hello on this computer. It says which will be refused: passkeys saved by a password manager, such as iCloud Keychain or Google Password Manager, and a phone's own passkeys. It says how to set a PIN on a new security key when the browser does not offer to. It asks for the key's name, and says the key will show that name, so it should not be an email or a real name. It offers two buttons. "Register a security key" sends `kind: security_key`. "Use Windows Hello on this computer" sends `kind: this_device`, and the page says to choose Windows Hello or this device in the browser's dialog. Each refusal is explained in words: `staff_key_not_device_bound` means the browser saved a synced passkey, `staff_key_not_user_verified` means the key asked for no PIN or fingerprint, and `staff_key_refused` means the browser's answer could not be checked. The page says the link still works. After either of the first two refusals, and only when the enrolment options say that the console's relying party ID is not the app's (`rpShared` false), the page calls `PublicKeyCredential.signalUnknownCredential({ rpId, credentialId })` for the credential it has just created, where the browser has the call (Chrome and Edge 132+, Safari 26), so the password manager drops the refused passkey. Where the browser lacks the call, or the two IDs are shared, the page tells the person to delete the console's entry from their password manager by hand. The WebKit bugs that kept 1c from the Signal API (322267 and 302624) delete other passkeys only on the same relying party ID, and outside development the console's ID holds no synced passkey that korbat accepts; in development both IDs are `localhost`, where the call could delete the developer's app passkeys, so the page does not make it there. Sign-in never calls it, because every failure before the signature gets one answer. A failed sign-in says to choose the security key or Windows Hello rather than a password manager's passkey.

The console sends `X-Staff-Activity: 1` on every request a person's action starts, and on no other. Its only timed requests are the two reads of its idle timer, which carry no mark. The timer restarts at 15 minutes, or at the time left to the session's absolute end when that is less, whenever an activity-marked request succeeds. Two minutes before it runs out (at 13 minutes of a full idle period) the console reads `GET /api/staff/me`: when more than two minutes are left (the person acted in another tab of the same session), it sets the timer from the answer's seconds left; otherwise it shows, in a live region, "Your staff session ends in 2 minutes." with a "Stay signed in" button that sends one activity-marked `GET /api/staff/me`. When the absolute end is the nearer one, the warning instead reads "Your staff session ends at 21:40. Sign in again with your staff key then." and has no button, since nothing moves the absolute end. When the timer runs out it reads `/me` once more and either sets the timer from the answer or shows sign-in. Any `staff_session_required` answer shows the sign-in screen in place with "Your staff session ended" and keeps the path; after the sign-in the console returns to that path. A later screen that refreshes itself (3c's queue) sends its refreshes without the mark, and 3c keeps a draft in memory across a sign-in by the same account.

The build writes `dist/index.html` and hashed bundle and stylesheet files; esbuild's options pin the target and minify.

## 10. Contracts

`packages/contracts/src/staff.ts` holds: the enrolment, sign-in and step-up requests and answers (WebAuthn JSON through the existing schemas; the enrolment options request is `{ token, name, kind }`, with `kind` one of `security_key` and `this_device`, and its answer also says whether the console's relying party ID is the app's (`rpShared`); the step-up options request is `{ action, target, params }`); `STAFF_STEP_UP_ACTIONS`, each step-up action's name, target type and the zod schema of its params, read by the step-up options, `requireStaffStepUp`, `audit-verify` and the console (3a: `staff_session_revoked`, a staff session as target, params `{}`); the action's sorted-JSON text and the step-up challenge's layout (its offsets and purpose code), which the API, `audit-verify` and the console share; the stored assertion's shape; `StaffMe` (with the session's handle, `idleSecondsLeft` and `absoluteSecondsLeft`), `StaffSession` (with `browser`), `StaffKey`, `AuditEntry` and `AuditPage` (with the `at` request); and `StaffErrorCode`.

`StaffErrorCode` lists `staff_session_required`, `staff_key_invalid`, `staff_key_suspended`, `staff_key_limit`, `staff_key_not_device_bound`, `staff_key_not_user_verified`, `staff_key_refused`, `staff_enrollment_invalid`, `staff_step_up_required` and `staff_step_up_invalid`. `staff_key_invalid` covers an unknown or revoked key, an account that is no longer live or staff, a sign-in challenge the codec refuses and a response the library refuses, with one answer for all. The auth module raises these codes: `AuthErrorKind` becomes `AuthErrorCode | StaffErrorCode | "invalid_request"`, and `MESSAGES` (`apps/api/src/auth/context.ts`) gains their messages, so `app.ts`'s error handler needs no new branch. Staff routes may also answer the shared `challenge_expired`, `rate_limited` and `invalid_request`, and the staff gate's `not_found` and `csrf_failed`. They never answer a `passkey_*` code, whose messages send people to remedies the console does not have: the staff flows catch the codec's and the wrapper's `passkey_invalid` and `passkey_unsupported` and raise `staff_key_invalid` at sign-in, `staff_step_up_invalid` at step-up and `staff_key_refused` at enrolment. Where only the operator can help, the messages say so.

- `staff_session_required`: "Your staff session ended. Sign in with your staff key."
- `staff_key_invalid`: "This key does not open the staff console. If it should, ask the operator to check your staff keys."
- `staff_key_suspended`: "This staff key was switched off because a copy of it may exist. Ask the operator for a link to enrol a new one."
- `staff_key_limit`: "This account has 5 staff keys. Ask the operator to revoke one before enrolling another."
- `staff_key_not_device_bound`: "This key can be synced or copied, so it cannot be a staff key. Use a security key or a device-bound authenticator."

## 11. Security and privacy

What stays impossible even for an admin, and what proves it (`threats.md` 3.3.1): no route changes a role (a route-table test); no route acts as another user or reads another user's sessions, email, IP, device or phone (a route-table test and the architecture rule); no audit row can be changed, removed or placed out of the chain by the API role (database tests: UPDATE, DELETE and TRUNCATE on `audit_log`; any write to or lock on `audit_head`; `session_replication_role`; disabling the trigger; a temporary `audit_head`; an insert naming an existing id; supplied chain columns), and a change by the owner `korbat_migrate` or the superuser to rows a kept head covers is detected by `audit-verify` against that head; no staff power without a staff session, on the console's origin, from a staff key whose authenticator reported UV and no BE (integration tests with the software authenticator, including a key reporting BE refused at enrolment and at sign-in, a key reporting no UV refused, a response without the owner's user handle refused, a personal passkey refused, an assertion from the app's origin refused, an app session cookie refused, a bearer token refused); no staff answer readable or actionable from another origin: staff routes carry no CORS headers, the staff gate refuses a foreign Origin or a `Sec-Fetch-Site` other than same-origin on every method, and the configuration refuses the console's origin in the app's trusted origins (HTTP and configuration tests); no action confirmed by an assertion made for another (a step-up test), and no key asked to sign a step-up whose challenge binds another action than the one the person chose (the console's tests and the browser check); no staff key or staff session left live, and no unused enrolment left, after a demotion or a deletion, and no key enrolled by a link issued before a `revoke ... all`, a demotion or a deletion (integration tests); no page left open keeping a staff session past 15 minutes without an action by its person (an integration test and the console's timer tests). No staff key exists without an enrolment the command line issued, and no code in the API can add one, delete one or revive a revoked or suspect one (database tests as `korbat_auth`). No row of a step-up action is in the record, whatever its actor, without an assertion that `audit-verify` checks against a key of that row's actor (audit tests), and no staff session pairs an account with another account's key (a database test). Every auth-side fact commits or rolls back together with its audit row (an audit test). Rows without a step-up, such as sign-ins and sign-outs, remain the API's word.

What the flags cannot prove: without attestation, UV and BE are claims the authenticator makes about itself, so a software authenticator that reports BE=0 while its key can be copied would pass. That residual is left to three things. The runbook lists the authenticators staff use: a FIDO2 security key with a PIN, or Windows Hello on a computer with a TPM. The operator hands over each enrolment link. `staff.js keys` prints each key's reported AAGUID, which is zeros when the browser or the authenticator withholds it.

Staff keys are never shown in full; the audit reader never returns metadata that names a person beyond the actor's handle.

## 14. Success criteria

1. Nothing gives staff powers but a staff session on the console's origin from a staff key whose authenticator reported UV and no BE, and every test in section 11's list passes.
2. Staff keys exist only through enrolments the command line issued, which the database enforces; keys are revoked from the command line (`staff.js revoke` or a demotion by grant-role), by an account's take-down, or by a counter regression, which also marks them suspect; and every enrolment issued or cancelled, key, sign-in, sign-out, revocation and role change is in the audit log, written in the same transaction as its change.
3. The audit log is a hash chain the API role can only extend, in an order and at times the database alone sets; `audit-verify` recomputes it in its own code, and a change made by any role, the owner and the superuser included, to a row at or before a kept head is detected when `audit-verify` runs with that head; and every row of a step-up action in it carries an assertion that `audit-verify` checks against the public key of a key its actor holds.
4. The console runs under the strict policy of section 3 with no violation in the committed browser check of section 12, over every screen with hostile fixtures, and renders every user string as text.
5. The app is unchanged for everyone but staff, whose staff powers are gone from it.

## 15. Amendments from the dry run (2026-10-01)

Found while the tasks were dry-run in the scratch clone, by the conformance review of each task, by the adversarial review of the range and by a walk-through in a real browser; each is applied in the prompts. Where an amendment and a section above differ, the amendment is current.

- **"Has a handle" is the auth side's record (section 6, `auth.add_staff_key`).** The function checks `auth.users.onboarded_at is not null`, which onboarding sets right after the profile and its handle exist; it never reads `public.profiles`.
- **One policy per staff table (section 6).** Each auth staff table has one `FOR ALL` policy for `korbat_auth`; a single narrower policy cannot serve the reads, updates and deletes the role needs, and the grants do the restricting.
- **Set values stay set (section 6).** The never-cleared trigger refuses to clear or change a set `revoked_at`, `suspect_at` or `used_at`, so every revocation sets `revoked_at` only where it is still null; a check constraint, `staff_keys_suspect_is_revoked`, keeps `suspect_at` from being set without `revoked_at`.
- **`CONSOLE_ORIGIN` is written as a browser sends it (section 8).** Scheme, host and port only: lowercase, no path, no trailing slash, no default port, because the staff gate compares the `Origin` header with it as a string; equality with `APP_ORIGIN` and the `TRUSTED_ORIGINS` entries is judged by origin; production also refuses an IP address or `localhost` for the console, as for the app; a `CONSOLE_RP_ID` set while `CONSOLE_ORIGIN` is unset is kept.
- **The functions' answers (section 6).** `auth.add_staff_key` returns the key's id, `auth.append_audit` the row's `chain_seq`, and `auth.forget_staff_keys` how many keys it blanked; refusals raise the staff error code itself as the message (`staff_enrollment_invalid`, `staff_key_limit`), which the flows map; a `staff_key_added` row's metadata is `{"enrollmentId": ...}`, never the key's name or AAGUID.
- **Contracts the design left open (section 10).** `StaffEnrollVerifyResponse` is `{ key: StaffKey }`, `StaffSignInVerifyResponse` is `StaffMe`, `AuditPageQuery` refuses `cursor` and `at` together, `StaffMe` refuses an idle end later than the absolute end, and `STAFF_AUDIT_PAGE_SIZE` is 50.
- **Grant-role's first statement locks the account (section 7, Role changes).** It is a `SELECT ... FOR NO KEY UPDATE` of the account's row, which takes the same lock as the role's update, because the `role_granted` row needs the previous role, which `UPDATE ... RETURNING` does not give.
- **`audit-verify`'s session settings (section 7, Command line).** It sets `DateStyle` ISO, `TimeZone` UTC and the 10-second `lock_timeout` with `SET LOCAL` at the start of its verifying transaction, so the same check runs inside a transaction a test hands it (`checkAuditRecord(tx, kept, keysFrom)`, whose keys come from the auth role when the handed transaction is on the API's).
- **What `audit-verify` also refuses (section 7).** Rows at a place of 0 or below, rows beyond the head, and kept places that name no row.
- **Each command reads only its own settings (section 7).** `staff.js` never loads the API's configuration: `audit-head` reads `DATABASE_URL_API`, `audit-verify` that and `DATABASE_URL_AUTH`, each through a narrow schema (`staffDatabaseUrls`), so it runs with the console off, moved or misconfigured; `config.ts` exports the PostgreSQL URL rule both use.
- **Bundle entries never import each other (section 5).** In a bundle every module's `import.meta.url` is the bundle's, so an entry that imported another entry's file would run that entry's main too; the lock-timeout helpers live in `cli/lock-timeout.ts`, `SYSTEM_ACTOR_ID` moved to `auth/admin.ts`, and `build.mjs` says so.
- **The gate's answers (section 7, The staff gate).** Another Host gets the app's own unknown-route 404 (`c.notFound()`), compared exactly, without lowercasing; a failed Origin or `Sec-Fetch-Site` test is `AuthError("csrf_failed", 403)`.
- **The reader past the head (section 7, The audit log).** For an `at` beyond the head the reader returns the newest page.
- **Who the take-down's record names (section 7).** The account itself in `takeDown`, since its owner asked for the deletion, and the system actor in `finishTakeDown`, which the purge job runs; `finishTakeDown` now takes the account's row first with `FOR NO KEY UPDATE`, as every writer of staff rows does.
- **The shapes of the staff record's rows (section 7).** `staff_key_revoked`: target `staff_key`, metadata `{ keyId, sessionsRevoked, via }`, `key_id` null; `staff_enrollments_cancelled`: target `user`, metadata `{ count, via }`; an enrolment issued by `staff.js enroll`: target `user`, metadata `{ enrollmentId, via: "cli" }`.
- **The take-down's enrolments (section 7).** It deletes every enrolment, spent ones too, and its `staff_enrollments_cancelled` row counts only the links that were still open, written only when there was one.
- **`staff.js keys` without an email (section 7).** It lists live accounts whose role is not `user`, and reads their handles on the API's role, so it needs both database URLs.
- **The command line's mailer (section 7).** `cli/mail.ts` builds it from `SMTP_URL` and `MAIL_FROM`; grant-role uses it, and its result gains the staff counts and `mailError`.
- **No limit of its own on enrolment (section 7).** The enrolment routes have only the global rate limit; the link's 30 minutes and single use bound them.
- **BS without BE is malformed (section 7, Sign-in).** @simplewebauthn/server 14.0.2 rejects an assertion that reports BS without BE before the flow sees its flags, so that case answers `staff_key_invalid`; BE, backed up or not, answers `staff_key_not_device_bound` as designed.
- **The marked read is an update (section 7, Every staff request).** A request marked `X-Staff-Activity: 1` reads and slides its session in one `UPDATE ... FROM` the staff keys joined to the users; the account is reached as the key's owner, which the sessions' foreign key on `(key_id, user_id)` makes the session's account.
- **An expired sign-in challenge (section 7, Sign-in).** It answers the shared `challenge_expired`, as enrolment does, which section 10 allows; forged, other-purpose and spent challenges answer `staff_key_invalid`.
- **The sign-in record's shapes (section 7).** `staff_sign_in` and `staff_signed_out` rows: the account as actor, the session as target (`staff_session`, its handle), the handle and the key in their columns, metadata `{}`; their auth events carry `{ keyId, handle }` and `{ handle }`; `staff_key_counter_regression`: the key's owner as actor, the key as target, metadata `{ keyId, sessionsRevoked, via }`.
- **What the console reads (section 7, Sessions and keys).** `GET /api/staff/keys` lists live keys only, since `StaffKey` has no revoked field; sign-in options have only the global rate limit.
- **`staff.js revoke`'s edges (section 7, Command line).** An already revoked key exits 0 having written nothing and mailed nothing, and so does `all` with nothing left; an unknown account, or a key that is unknown or another account's, exits 1; it reads `DATABASE_URL_AUTH`, `SMTP_URL`, `MAIL_FROM` and `NODE_ENV` only.
- **The step-up middleware validates the body (section 7, Step-up).** `requireStaffStepUp` validates the action's strict params with an optional `stepUp` through the shared validator, so a missing assertion answers `staff_step_up_required` rather than `invalid_request`; the route reads the confirmed result from `staffStepUp`.
- **Status codes (sections 7 and 10).** `staff_step_up_required` and `staff_step_up_invalid` answer 403; a handle that names no live session of the person's own answers `404 not_found` ("No such session"), as the app's own session revocation does.
- **The re-check before the action (section 7, Step-up).** The revocation's transaction locks the account's row, then checks that the confirming key and the account are still live, answering `staff_session_required` and writing nothing otherwise; a person may revoke the session they confirm from.
- **Lower-case targets (section 10).** A step-up target id is PostgreSQL's lower-case uuid only (`LowerCaseUuid`); any other spelling is refused with `invalid_request`, because the record hashes the target exactly as confirmed and stores the database's form.
- **`staff_session_required` clears the cookies wherever it is raised (section 7).** `requireStaff` checks `c.error` after `next()`, since Hono hands an error thrown behind it to `app.onError`, and clears both staff cookies on the answer.
- **A step-up challenge needs a minute left (section 7, Step-up).** It carries the full 10 minutes, but is read only while more than one minute is left (`STEP_UP_READ_MARGIN_MS`), so a confirmed row is never written after the expiry `audit-verify` checks; the margin assumes the API's and the database's clocks agree.
- **What `audit-verify` also checks (section 7).** That the stored `action_hash` equals the recomputed one, and it reports a challenge used twice as its own problem; it does not check `metadata.params` against the action's schema.
- **The console's type declarations (section 9).** There is no `@types/react-dom` in the lockfile, so `src/react-dom.d.ts` declares `react-dom/client` and `react-dom/server`, as the app's tests do; `@types/react` 19.2.18 and `@types/node` 24.13.5, both already locked, are its devDependencies.
- **"Your staff session ended" (section 9).** It shows when the page held a session, or when the refused request carried the staff CSRF cookie (read before sending, since the 401 clears it), so a reload or a new tab after an idle end says so too; a 401 with neither (never signed in, signed out, past the cookie's 12 hours) shows plain sign-in.
- **The home screen's 7 days (section 9).** Opening Home does one marked `GET /api/staff/me` and counts the 7 days back from that answer's server time, not from the session read at sign-in.
- **The console's own checks (section 9).** The step-up check also checks the challenge's version byte, and every ceremony forces user verification "required", attestation "none" and no extension but `credProps`, whatever the server's options say; the staff CSRF header goes on every request while the cookie exists.
- **The console site's headers live in `apps/admin/site-headers.mjs` (sections 8 and 9).** The development server uses them; Task 7's Caddyfile and the scan that compares them must match.
- **The app's site refuses staff paths with two handles (section 8).** Caddy 2.11.4 sorts `handle` blocks by their path's length and compares paths only when a handle matches exactly one, so one handle matching both `/api/staff` and `/api/staff/*` is not reliably placed ahead of `handle /api/*`; two one-path handles, longer than `/api/*`, always are. The refusal is a shared snippet that answers the API's error envelope without a request id, which is how the smoke test tells Caddy's answer from the API's.
- **`immutable` only on real build files (section 8).** The console site's hashed-file rule adds Caddy's `file` condition to `path /assets/*`, so the `index.html` fallback served for a missing hashed name keeps `no-store, no-transform`.
- **The browser check's reach (section 12).** Beyond the screens section 12 lists, it covers an unknown address, sign-out and the enrolment refusal of a synced passkey; CI runs it with `KORBAT_BROWSER_CHANNEL=chrome`.
- **Every ceremony's challenge is checked before the key is asked (sections 5, 9 and 11; found by the review).** The contracts export the 58-byte layout (`CEREMONY_CHALLENGE`) and every purpose code (`CHALLENGE_PURPOSES`) beside `STAFF_STEP_UP_CHALLENGE`, and the codec reads them from there. Before every `navigator.credentials` call the console checks the challenge: at sign-in 58 bytes, version 1, purpose `staff_signin` and a zero binding; at enrolment 58 bytes, version 1, purpose `staff_register` (its binding names the enrolment, which the page is never told, so it cannot be checked there); at step-up the 74-byte check. No key is asked at sign-in or enrolment to sign another ceremony's challenge.
- **`audit-verify` reads every row (section 7, Command line; found by the review).** It pages on `(chain_seq, id)` and, in the same snapshot, fails on a place held by two rows, a row with no place, or a row count that does not equal the rows read plus the rows beyond the head.
- **Keys are judged by where they were enrolled (sections 2 and 7; found by the review).** A key whose recorded origin or relying party ID differs from the running configuration is `staff_key_invalid` at sign-in, before the signature, and `staff_step_up_invalid` at the step-up's options and confirmation; assertions are verified against the key's recorded values. Moving the console means enrolling every key again, and the API enforces it.
- **The enrolment page signs in with the new key itself (sections 2 and 9; found by the review).** Its "Sign in with this key" button narrows the allowed credentials to the key just registered and signs in whatever session the browser holds, so the check after each enrolment always uses the new key.
- **A confirmed action never lands after its expiry (sections 2 and 7; found by the review).** The confirmed revocation's transaction sets `lock_timeout` to the lesser of 15 seconds and a third of the challenge's remaining life by the database's clock, and the statement that writes its audit row reads the database's clock after the insert and undoes everything when the challenge has expired; a late confirmation writes nothing and answers `challenge_expired`. The one-minute read margin no longer assumes the API's and the database's clocks agree.
- **`auth.forget_staff_keys` blanks only revoked keys (section 6; found by the review).** Migration 0013 restates it so it blanks the name, AAGUID and transports only of keys whose `revoked_at` is set, of an account marked deleted; the take-down revokes them earlier in the same transaction, and code in the API gains nothing it cannot already do by revoking.
- **Revocation order and grant-role's after-commit steps (section 7, Role changes; found by the review).** Demotion and take-down revoke keys before staff sessions, as `staff.js revoke` does, so a concurrent sign-in cannot keep an unrevoked session; grant-role's cache tombstones and its mail run as independent best-effort steps after the commit, each reported as a warning, and the command exits 0 once the change is committed.
- **Smaller fixes (sections 7 and 9; found by the review).** `staff.js keys` reads in read-only transactions with a 10-second lock timeout; the console reads a marked `/me` right before the step-up options and every `/me` answer replaces the page's session; Go to place says when there is no row at the place asked for; an older Load older's answer never joins a page opened after it; the browser check's fixtures answer with the API's own statuses.
